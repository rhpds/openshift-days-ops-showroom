= Zero-Trust Database Access with SPIFFE mTLS
:page-toclevels: 1

== Module Overview

**Duration:** 20 minutes +
**Format:** Hands-on lab +
**Audience:** Security Engineers, Platform Engineers, IT Operations

include::partial$console-access.adoc[]

Your payment-processing service needs to reach PostgreSQL. The database team refuses to hand out another shared password in a Kubernetes `Secret`—and they're right to push back. Static credentials in Git, images, or long-lived Secrets are exactly what attackers hunt for after a breach.

In the previous module you centralized secrets with Vault. Here you go one step further: **no database password at all**. The **Zero Trust Workload Identity Manager (ZTWIM)** issues short-lived X.509 certificates bound to each workload's Kubernetes identity. PostgreSQL trusts those certificates instead of a password vault entry.

By the end of this lab you will:

* Configure ZTWIM for the lab using the workshop setup scripts
* Deploy PostgreSQL with SPIFFE-issued certificates and a separate client workload identity
* Establish mutual TLS (mTLS) database connections using short-lived SPIFFE certificates instead of passwords
* Inspect certificate properties, identity binding, and automatic certificate rotation
* Verify that every SPIRE agent attested with `k8s_psat`, that each agent is tied to a real cluster node, and that each PostgreSQL registration entry is parented to one of those agents
* Confirm that connections without valid certificates are rejected

Zero-trust principles require cryptographic proof of workload identity. SPIFFE (Secure Production Identity Framework for Everyone) is the open standard behind this approach; ZTWIM brings SPIRE—the SPIFFE runtime—to OpenShift so every pod gets a cryptographic identity without you managing a private CA by hand.

[cols="1,2,2",options="header"]
|===
|Area | Risk If Ignored | Analogy
|Static Database Passwords | Credential theft enables persistence | Master key copies floating everywhere
|Password-Based Auth | Brute force / spray attacks | Guessable combination lock
|Network-Only Security | Lateral movement after breach | Locked front door, open internal doors
|Manual Cert Rotation | Stale credentials remain valid | Expired building access badges still work
|No Mutual Authentication | Server cannot verify client | One-way ID check at secure facility
|===

== Inspect SPIFFE certificates

Before connecting, look at what ZTWIM actually issued. Certificates are automatically mounted at `/opt/postgresql-certs/` by the `spiffe-helper` sidecar—you never create or copy PEM files by hand.

. On the **server** pod, dump the certificate and focus on three fields—*who* it represents, *how long* it's valid, and the canonical SPIFFE identity URI:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe -c postgresql-spiffe deployment/postgresql-spiffe \
  cat /opt/postgresql-certs/svid.pem | openssl x509 -noout -text
----
+
Look for these in the output:

* *Subject* — server hostname (`CN=postgresql-spiffe.postgresql-spiffe.svc`)
* *Validity* — short lifespan (default: 1 hour); `Not After` is roughly one hour after `Not Before`
* *Subject Alternative Name* — DNS name and SPIFFE ID URI:
+
[source,text]
----
X509v3 Subject Alternative Name:
    DNS:postgresql-spiffe.postgresql-spiffe.svc
    URI:spiffe://<trust-domain>/ns/postgresql-spiffe/sa/postgresql-spiffe
----

The SPIFFE ID format is `spiffe://<trust-domain>/ns/<namespace>/sa/<serviceaccount>`. In production, auditors often ask for the SPIFFE ID URI—not just the CN—because it binds identity to Kubernetes namespace and service account.

. List the certificate files on the server. You should see three files owned by `postgres`:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe -c postgresql-spiffe deployment/postgresql-spiffe \
  ls -la /opt/postgresql-certs/
----
+
* `svid.key` — private key (`600` permissions, readable only by `postgres`)
* `svid.pem` — workload certificate
* `svid_bundle.pem` — CA bundle for verification
+
. On the **client** pod, run the same inspection and compare identities side by side:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe-client -c postgresql-spiffe-client deployment/postgresql-spiffe-client \
  cat /opt/postgresql-certs/svid.pem | openssl x509 -noout -text
----
+
The client CN must match the PostgreSQL database user:
+
[source,text]
----
Subject: C=US, O=SPIRE, CN=postgresql_spiffe
----
+
Each workload gets a unique SPIFFE ID:

* *Server*: `spiffe://.../ns/postgresql-spiffe/sa/postgresql-spiffe`
* *Client*: `spiffe://.../ns/postgresql-spiffe-client/sa/postgresql-spiffe-client`
+
. Check when the client certificate expires:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe-client -c postgresql-spiffe-client deployment/postgresql-spiffe-client \
  sh -c 'echo "Current time: $(date)"; openssl x509 -in /opt/postgresql-certs/svid.pem -noout -dates'
----

The `spiffe-helper` sidecar fetches a new certificate approximately 30 minutes before expiration. Short lifetimes are a feature—if an attacker steals a cert, the window of abuse is measured in minutes, not months until someone rotates a password.

== See how the identity was attested

The certificate you just read is only meaningful if SPIRE was right to issue it. Workload selectors decide which pod may receive an identity. The SPIRE agent on the node is the component that reports which pod called the Workload API, so that agent has to prove it belongs on this cluster before its report counts.

*The proof is a projected service account token that the kubelet minted for the SPIRE agent pod.* 

The SPIRE server validates that token with the Kubernetes TokenReview API and records what the API server returns: cluster, agent namespace, agent service account, and node name. The agent's SPIFFE ID is `spiffe://<trust-domain>/spire/agent/k8s_psat/<cluster>/<node-uid>`. That ID is bound to the node. Workload certificates are issued only with that attested agent as their Parent ID. A node that fails the check receives no agent identity, and pods on that node receive no certificates. A stolen workload certificate still expires in about an hour. Minting a new one requires a node the API server will vouch for.

[IMPORTANT]
====
Node attestation is what makes the database certificate trustworthy. SPIRE issues the `postgresql-spiffe-client` certificate only after the Kubernetes API server has validated the agent on that node. A machine that fails the check never receives an agent identity, so it cannot mint a client certificate that would pass the `sslmode=verify-full` connection in the next section.
====

=== Verify node attestation

Confirm the control is on, that every SPIRE agent passed it, and that the attested identity is pinned to a real node in this cluster. Each command locates the operator namespace on its own, so you can re-run a step in a new terminal.

. Find the namespace where ZTWIM installed SPIRE:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
ZTWIM_NS=$(oc get spireserver -A -o jsonpath='{.items[0].metadata.namespace}')
echo "$ZTWIM_NS"
----
+
The name is `openshift-zero-trust-workload-identity-manager` or `zero-trust-workload-identity-manager`.
+
. Confirm projected service account token (PSAT) node attestation is enabled. The output is the single word `true`:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
ZTWIM_NS=$(oc get spireserver -A -o jsonpath='{.items[0].metadata.namespace}')
oc get spireagent cluster -n "$ZTWIM_NS" -o jsonpath='{.spec.nodeAttestor.k8sPSATEnabled}{"\n"}'
----
+
[source,text]
----
true
----
+
. List the SPIRE agent pods, then list the agents the SPIRE server has attested:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
ZTWIM_NS=$(oc get spireserver -A -o jsonpath='{.items[0].metadata.namespace}')
echo "Running SPIRE agent pods: $(oc get pods -n "$ZTWIM_NS" -l app.kubernetes.io/name=spire-agent --field-selector=status.phase=Running --no-headers | wc -l | tr -d ' ')"
oc get pods -n "$ZTWIM_NS" -l app.kubernetes.io/name=spire-agent
oc exec -n "$ZTWIM_NS" spire-server-0 -c spire-server -- \
  /opt/spire/bin/spire-server agent list \
  -socketPath /tmp/spire-server/private/api.sock
----
+
The trust domain, node UID, serial number, and expiration time differ on your cluster. The shape of each entry looks like this:
+
[source,text]
----
SPIFFE ID         : spiffe://<trust-domain>/spire/agent/k8s_psat/<cluster>/<node-uid>
Attestation type  : k8s_psat
Expiration time   : <timestamp in the future>
Serial number     : <serial>
Can re-attest     : true
----
+
Confirm all of the following:
+
* The number of attested agents equals the number of `Running` `spire-agent` pods, and that number is at least 1.
* Every entry says `Attestation type: k8s_psat`. Any other type means a node was trusted without the API server check.
* Every SPIFFE ID contains `/spire/agent/k8s_psat/`.
* `Expiration time` is later than the current time. Node identity expires. An expired agent is no longer attested.
+
. Show the cluster nodes, then show the first attested agent. The command selects the first agent from the list. The same checks apply to every agent:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
ZTWIM_NS=$(oc get spireserver -A -o jsonpath='{.items[0].metadata.namespace}')
echo "Operator namespace: ${ZTWIM_NS}"
oc get nodes -o custom-columns=NAME:.metadata.name,UID:.metadata.uid --no-headers
AGENT_ID=$(oc exec -n "$ZTWIM_NS" spire-server-0 -c spire-server -- \
  /opt/spire/bin/spire-server agent list \
  -socketPath /tmp/spire-server/private/api.sock \
  | awk '/SPIFFE ID/ { print $NF; exit }')
echo "Attested agent: ${AGENT_ID}"
oc exec -n "$ZTWIM_NS" spire-server-0 -c spire-server -- \
  /opt/spire/bin/spire-server agent show \
  -socketPath /tmp/spire-server/private/api.sock \
  -spiffeID "${AGENT_ID}"
----
+
Confirm all of the following on the agent you inspected:
+
* `k8s_psat:agent_node_name:<name>` matches a name from `oc get nodes`. The API server supplied that name.
* The node UID at the end of the agent SPIFFE ID matches the UID of that same node.
* `k8s_psat:agent_ns:<namespace>` is the operator namespace printed above.
* `k8s_psat:agent_sa:spire-agent` is the SPIRE agent service account. The token was minted for the agent. The PostgreSQL client service account cannot present it.
* `Can re-attest: true`. When the attestation expires, the agent must prove itself to the API server again.
+
A machine that cannot produce that token never appears in the agent list, and nothing on that machine can be issued a PostgreSQL client certificate.

=== Verify workload attestation

Node attestation decides which machines may ask for identities. Workload attestation decides which pods on those machines receive the PostgreSQL certificate.

. Show the client registration policy. The namespace, pod label, and SPIFFE ID template are the rules the agent enforces:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get clusterspiffeid postgresql-spiffe-client \
  -o jsonpath='namespace={.spec.namespaceSelector.matchLabels.kubernetes\.io/metadata\.name}{"\n"}pod-label={.spec.podSelector.matchLabels.app}{"\n"}template={.spec.spiffeIDTemplate}{"\n"}'
----
+
Expected output:
+
[source,text]
----
namespace=postgresql-spiffe-client
pod-label=postgresql-spiffe-client
template=spiffe://{{ .TrustDomain }}/ns/{{ .PodMeta.Namespace }}/sa/{{ .PodSpec.ServiceAccountName }}
----
+
The template is the SPIFFE ID you saw in the client certificate URI. The selectors restrict that ID to this namespace and to pods labeled `app=postgresql-spiffe-client`.
+
. Show the live registration entry for the client:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
ZTWIM_NS=$(oc get spireserver -A -o jsonpath='{.items[0].metadata.namespace}')
oc exec -n "$ZTWIM_NS" spire-server-0 -c spire-server -- \
  /opt/spire/bin/spire-server entry show \
  -socketPath /tmp/spire-server/private/api.sock \
  -selector k8s:ns:postgresql-spiffe-client
----
+
Confirm all of the following. Extra selectors, such as pod name or pod UID, may also be present:
+
* The SPIFFE ID matches the certificate URI from the previous section: `spiffe://<trust-domain>/ns/postgresql-spiffe-client/sa/postgresql-spiffe-client`.
* The Parent ID is one of the `k8s_psat` agent SPIFFE IDs from the node attestation list. That parent is the proof that node attestation is in the chain. SPIRE issued the certificate under an agent the API server already validated.
* Selectors include `k8s:ns:postgresql-spiffe-client`, `k8s:sa:postgresql-spiffe-client`, and `k8s:pod-label:app:postgresql-spiffe-client`.
+
. Repeat the check for the database server:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
ZTWIM_NS=$(oc get spireserver -A -o jsonpath='{.items[0].metadata.namespace}')
oc exec -n "$ZTWIM_NS" spire-server-0 -c spire-server -- \
  /opt/spire/bin/spire-server entry show \
  -socketPath /tmp/spire-server/private/api.sock \
  -selector k8s:ns:postgresql-spiffe
----
+
Apply the same three checks to `spiffe://<trust-domain>/ns/postgresql-spiffe/sa/postgresql-spiffe`. The Parent ID is again a `k8s_psat` agent ID. The selectors name the `postgresql-spiffe` namespace, service account, and `app=postgresql-spiffe` pod label.

The mutual TLS connection in the next section uses a certificate SPIRE issued only after both of these checks. A pod that misses the selectors never receives an SVID, which is why the unauthorized pod later in this lab cannot connect. PostgreSQL still maps the certificate common name to the database user. Attestation is what made SPIRE willing to issue the certificate.

== Connect and verify mutual TLS

Time to put the certificates to work. You'll connect from the client pod using `psql` with `sslmode=verify-full`: the client proves its identity, PostgreSQL proves *its* identity, and hostname verification must pass. No password prompt—because there is no password.

. Run a one-line connection test:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe-client -c postgresql-spiffe-client deployment/postgresql-spiffe-client \
  psql "host=postgresql-spiffe.postgresql-spiffe.svc port=5432 user=postgresql_spiffe dbname=testdb sslmode=verify-full sslcert=/opt/postgresql-certs/svid.pem sslkey=/opt/postgresql-certs/svid.key sslrootcert=/opt/postgresql-certs/svid_bundle.pem" \
  -c "SELECT current_user, current_database();"
----
+
Expected output:
+
[source,text]
----
   current_user    | current_database
-------------------+------------------
 postgresql_spiffe | testdb
(1 row)
----

That's the payoff: `current_user` is `postgresql_spiffe` because the certificate CN matched the database role. Key connection parameters: `user` must match the certificate CN; `sslmode=verify-full` is the strictest mode (server verified, hostname matched, client cert required); `sslcert`, `sslkey`, and `sslrootcert` point to the SPIFFE-issued files under `/opt/postgresql-certs/`.

. Gather evidence that TLS is actually in use:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe-client -c postgresql-spiffe-client deployment/postgresql-spiffe-client \
  psql "host=postgresql-spiffe.postgresql-spiffe.svc port=5432 user=postgresql_spiffe dbname=testdb sslmode=verify-full sslcert=/opt/postgresql-certs/svid.pem sslkey=/opt/postgresql-certs/svid.key sslrootcert=/opt/postgresql-certs/svid_bundle.pem" \
  -c '\conninfo' \
  -c 'SELECT ssl_is_used();' \
  -c 'SELECT version();'
----
+
Look for `SSL connection (protocol: TLSv1.3, ...)` in the output and `ssl_is_used` returning `t`. Cluster IP and PostgreSQL build string may differ on your environment.
+
. Prove you have a working session—insert a row and read it back:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe-client -c postgresql-spiffe-client deployment/postgresql-spiffe-client \
  psql "host=postgresql-spiffe.postgresql-spiffe.svc port=5432 user=postgresql_spiffe dbname=testdb sslmode=verify-full sslcert=/opt/postgresql-certs/svid.pem sslkey=/opt/postgresql-certs/svid.key sslrootcert=/opt/postgresql-certs/svid_bundle.pem" <<'SQL'
INSERT INTO test_table (name, text)
VALUES ('spiffe-test', 'Authenticated with certificates!');
SELECT * FROM test_table;
SQL
----

== Prove zero-trust enforcement

Zero trust means *verify every connection*, not "trust the internal network." If an attacker can reach port 5432, they should still fail without a valid SPIFFE identity.

. Deliberately omit the client cert and key from the connection string:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe-client -c postgresql-spiffe-client deployment/postgresql-spiffe-client \
  psql "host=postgresql-spiffe.postgresql-spiffe.svc port=5432 user=postgresql_spiffe dbname=testdb sslmode=require" \
  2>&1 | head -5
----
+
Expected error:
+
[source,text]
----
psql: error: connection to server at "postgresql-spiffe.postgresql-spiffe.svc" failed:
FATAL: connection requires a valid client certificate
----

Network connectivity alone is insufficient—PostgreSQL `pg_hba.conf` requires SSL *and* valid client certificates (`hostssl ... cert`), and no password bypass exists for the `postgresql_spiffe` user.

. Launch a random pod in the same namespace—no SPIFFE sidecar, no issued certificate—and try again:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc run unauthorized-client --image=registry.redhat.io/rhel9/postgresql-16:latest \
  -n postgresql-spiffe-client --command -- sleep infinity
oc wait --for=condition=Ready pod/unauthorized-client -n postgresql-spiffe-client --timeout=60s
oc exec -n postgresql-spiffe-client unauthorized-client -- \
  psql "host=postgresql-spiffe.postgresql-spiffe.svc port=5432 user=postgresql_spiffe dbname=testdb" \
  2>&1 | head -3
----
+
You should see `connection requires a valid client certificate`. Even pods in the same namespace cannot connect without valid SPIFFE certificates—NetworkPolicy might let them talk; PostgreSQL still says no.
+
. Clean up the test pod:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc delete pod unauthorized-client -n postgresql-spiffe-client
----

== Observe automatic certificate rotation

Static passwords rot until someone notices. SPIFFE certificates expire on a schedule—and `spiffe-helper` renews them before they do, without restarting your application containers.

.Procedure
. Start tmux with two panes:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
tmux new-session \; split-window -v \; attach
----
+
. In the first pane, follow `spiffe-helper` logs:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc logs -n postgresql-spiffe-client -l app=postgresql-spiffe-client -c spiffe-helper --tail=20 -f
----
+
. Press *Ctrl+b*, then *o* to switch to the second pane.
+
[IMPORTANT]
====
`Ctrl+b` is the tmux prefix key. `o` switches to the next pane.
====
+
. In the second pane, capture the current certificate serial number and expiry:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe-client -c postgresql-spiffe-client deployment/postgresql-spiffe-client \
  sh -c 'openssl x509 -in /opt/postgresql-certs/svid.pem -noout -serial -enddate'
----
+
[NOTE]
====
Rotation happens on a schedule tied to certificate lifetime (roughly 30 minutes before expiry). In a short lab you may see only the initial `X.509 certificates updated` event—that still confirms the sidecar is watching and writing certs.
====
+
. Re-check the serial number and confirm the database connection still works:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe-client -c postgresql-spiffe-client deployment/postgresql-spiffe-client \
  sh -c 'openssl x509 -in /opt/postgresql-certs/svid.pem -noout -serial -enddate'
oc rsh -n postgresql-spiffe-client -c postgresql-spiffe-client deployment/postgresql-spiffe-client \
  psql "host=postgresql-spiffe.postgresql-spiffe.svc port=5432 user=postgresql_spiffe dbname=testdb sslmode=verify-full sslcert=/opt/postgresql-certs/svid.pem sslkey=/opt/postgresql-certs/svid.key sslrootcert=/opt/postgresql-certs/svid_bundle.pem" \
  -c "SELECT 'Connection successful after rotation' AS status;"
----
+
. Exit tmux and return to the bastion host terminal:
.. Type `exit` or press *Ctrl-D* to leave the tmux session.
.. Press *Ctrl+C* in the first pane if `oc logs` is still running.
.. type `exit` to leave the tmux session.
+

Congrats! You've seen new serial number, same trust chain, uninterrupted access—that's operational zero trust without a 2 a.m. password rotation runbook.

== Wrap-up

**Great job!** You secured database access with cryptographic workload identity and mutual TLS. 

To summarize:

* *ZTWIM* on this cluster provides SPIRE server, agents, CSI driver, and OIDC discovery for workload identity.
* *SPIFFE workload identity* binds X.509 certificates to Kubernetes namespace and service account, replacing static database passwords.
* *Node attestation* (`k8s_psat`) makes the Kubernetes API server vouch for each SPIRE agent. An unattested machine cannot mint workload certificates, so it cannot obtain a PostgreSQL client certificate that would pass mutual TLS.
* *Workload attestation* limits those certificates to the PostgreSQL namespace, service account, and pod label. Mutual TLS is only as strong as that chain.
* *Mutual TLS* enforces bidirectional certificate verification—both client and server prove cryptographic identity.
* *Short-lived certificates* (approximately 1 hour) limit exposure windows and rotate automatically via `spiffe-helper` sidecars.
* *Zero-trust enforcement*: connections without valid SPIFFE certificates are rejected regardless of network access.

This is one step in a larger Zero-trust architecture. At Red Hat, we have a framework for building secure clusters called the https://github.com/validatedpatterns/layered-zero-trust[Layered Zero Trust Validated Pattern]. You can learn more about the pattern and how to build your own secure clusters by following the link.
